# AGENTS.md

## What this is

Client-side Minecraft mod ("Battle Music", package `me.lemon553311.battlemusic`). ONE source tree in `src/main/java` produces **30 jars** via [Stonecutter](https://stonecutter.kikugie.dev/): 15 Fabric + 6 Forge + 9 NeoForge targets spanning Minecraft 1.16.5–26.3. There are no tests or linters — verifying a change means making every tier *compile*.

## Commands

```sh
./gradlew build                            # active version only (see `stonecutter active "..."` in stonecutter.gradle.kts)
./gradlew :1.21.8-fabric:buildAndCollect   # one target: ":<mc>-<loader>:buildAndCollect"
./gradlew buildAndCollect                  # ALL 28 targets -> build/libs/<mod.version>/
```

- CI builds with `--configure-on-demand --no-daemon`; `gradle.properties` sets `-Xmx6G`.
- First build auto-downloads JDK toolchains (8/16/17/21/25 via foojay) plus real Minecraft/Forge maven artifacts — slow, network required.
- `versions/<id>/` directories are generated by Stonecutter; never hand-edit them.

## Multi-version rules

- Version/loader differences live in `//? if` comment directives inside the Java sources. Targets are named `<mc>-fabric|-forge|-neoforge`; the preprocessor sees the plain MC version, and the loader is exposed as constants `fabric`/`forge`/`neoforge` (e.g. `//? if forge && >=1.19 {`).
- Gate chains must stay **flat — never nested** (Java block comments cannot nest).
- Adding a target = entry in `settings.gradle.kts` + matching section in `stonecutter.properties.toml` (all per-tier dep pins and metadata live there) + the CI matrix in `.github/workflows/release.yml`.
- **1.16.5 compiles under Java 8**, so never use `var`, pattern-matching `instanceof`, arrow `switch`, `Set.of`, `Files.readString/writeString`, or SLF4J without a gate. Java floor per tier: 8 (1.16.5), 16 (1.17), 17 (1.18–1.20.4), 21 (1.20.5+), 25 (26.1+).

## API boundaries already encoded in gates (don't re-derive)

- HUD: `HudRenderCallback` <1.21.6 vs `HudElementRegistry` >=1.21.6. Draw target: `PoseStack` <1.20, `GuiGraphics` 1.20+. blit first arg: `ResourceLocation` <1.21.2, `Function<ResourceLocation, RenderType>` 1.21.2–1.21.5, `RenderPipeline` >=1.21.6.
- Registries: `Registry` <1.19.3 vs `BuiltInRegistries` >=1.19.3. Warden doesn't exist <1.19. `Component.literal` is 1.19+ (use `new TextComponent` below).
- 26.1+ ships non-obfuscated with renamed classes (`ResourceLocation`→`Identifier`). Don't import such classes across a gate — compare registry keys as strings (`.getKey(type).toString()`).
- NeoForge: `FMLEnvironment.dist` field became `getDist()` at NeoForge 21.9 (gate `neoforge && >=26.1`).

## Build scripts: three, deliberately

- `build.gradle.kts` (Architectury Loom): every target ≤1.21.8, all loaders (platform comes from `loom.platform` in each `versions/<id>/gradle.properties`).
- `build.fabric26.gradle.kts` (mainline Fabric Loom, non-obf mode) and `build.neoforge26.gradle.kts` (ModDevGradle): the six 26.1+ targets, wired via `.buildscript = ...` in `settings.gradle.kts`.
- Architectury Loom **cannot** build 26.1+ (requires mappings that no longer exist; upstream bug architectury/architectury-loom#328). Never declare two Loom-family plugins in one script — Kotlin DSL accessor generation breaks for *every* target, not just the special-cased ones.

## Code layout

- `BattleMusicClient` is the loader-neutral core (`init()` + static hooks); `BattleMusicForge`/`BattleMusicNeoForge` are thin `@Mod` bootstraps wiring events to it; `platform/Platform.java` abstracts loader-specific dirs. HUD features register per loader but share drawing code; the whole Cloth Config screen lives loader-neutrally in `config/ClothConfigScreen.java`.

## Metadata & dependency gotchas

- `fabric.mod.json`, `META-INF/mods.toml`, `META-INF/neoforge.mods.toml`, `pack.mcmeta` are templated by `processResources expand()` from `stonecutter.properties.toml`. The mods.toml → neoforge.mods.toml switch is exactly MC 1.20.5; NeoForge 1.20.4 needs `mod.fml_range` set or the jar is silently dropped from the mod list.
- Fabric API's mod id is version-dependent: `fabric` pre-1.19.3, `fabric-api` after — pinned per tier as `mod.fabric_api_id`. Wrong id = "fabric-api missing" crash even when installed.
- Verify dep pins against real Maven directory listings, not Modrinth's `version_number` field (Cloth Config's carries a `+fabric` suffix absent from actual artifacts). If the TerraformersMC maven 400s on a Mod Menu jar, set `deps.modmenu_from_modrinth = "true"` for that tier.
- Cloth Config's mod id is `cloth_config` (underscore) on Forge/NeoForge; it remains a soft dependency everywhere.

## Releasing

Pushing a `v*` tag triggers `release.yml`: builds all 30 targets in parallel and publishes to Modrinth + CurseForge (secrets `MODRINTH_TOKEN`/`CURSEFORGE_TOKEN`; mod version taken from the tag). Manual dispatch offers a `publish_test` checkbox = full dry run of both publish steps. Tagless/local builds fall back to `mod.version` in `stonecutter.properties.toml`.
